فاهمك جدًا. أنت دلوقتي مش بتسأل “أزود feature إيه؟”، أنت بتسأل سؤال أهم:

```text
إزاي أخلي النظام يعيش ويتراقب ويتصلح ويتطور من غير ما كل تعديل يبقى رعب؟
```

وده تفكير صح جدًا قبل production.

رأيي: أنت محتاج خطة من 4 محاور:

```text
1. Observability: أعرف إيه اللي بيحصل.
2. Analytics: أعرف الناس بتسأل عن إيه.
3. Maintenance: أعرف أعدل بسرعة من غير ما أكسر.
4. Cost Optimization: أعرف أحوّل المتكرر إلى local/FAQ/tools.
```

# إيه يحصل لما يظهر type جديد فعلًا؟

لو بعد مدة اكتشفت إن فيه نوع أسئلة غير موجود، مثل:

```text
"compare these perfumes"
```

وقتها تضيف type جديد:

```text
comparison_request
```

لكن ما تضيفش type لكل صياغة.

أمثلة types ممكن تضيفها مستقبلًا:

```text
comparison_request
gift_advice
sample_pack_request
complaint_or_return
skin_sensitivity_question
longevity_projection_question
```

لكن في البداية خليك بالـ 14 type اللي عندك + unknown.

---

# الـ LLM هيعرف يصنف الجديد؟

أيوه غالبًا، بشرط تعطيه:

```text
1. compact context
2. allowed question types
3. examples قليلة
4. confidence
5. fallback rule
```

مش لازم يكون مدرب على كل سيناريو.

لكن لا تثق فيه 100%.
خليه يقترح، وDart يتحقق.

---

# الشكل العملي المقترح

## Step 1

local classifier يحاول.

لو:

```text
confidence >= 0.85
```

ينفذ local.

## Step 2

لو أقل:

يروح LLM classifier/router.

## Step 3

LLM يرجع:

```json
{
  "questionType": "...",
  "confidence": 0.0-1.0,
  "tool": "...",
  "signals": [],
  "preferencePatch": {},
  "needsClarification": false
}
```

## Step 4

Dart يقرر:

```text
confidence عالي + tool valid => execute
confidence متوسط + safe tool => execute cautiously
confidence منخفض => ask clarification
unknown => ask clarification
```

---

# مثال كامل

المستخدم:

```text
عايز ريحة فنادق فخمة ومش خانقة
```

Local:

```text
مش exact
confidence=0.45
send_to_llm
```

LLM:

```json
{
  "questionType": "recommendation_request",
  "confidence": 0.84,
  "tool": "update_preferences_and_recommend",
  "preferencePatch": {
    "tags": ["clean", "luxury", "elegant", "soft_on_nose", "non_offensive"]
  },
  "signals": ["hotel_clean_scent", "luxury", "not_cloying"]
}
```

Dart:

```text
tool valid
search catalog
guard
cards
```

Analytics:

```text
pattern=hotel_clean_scent
knownPattern=false
handledBy=llm
success=true
```

بعد ما يتكرر 50 مرة:

```text
add local alias:
"ريحة فنادق" => clean + luxury + soft_on_nose
```

# الخلاصة

السؤال الجديد يعرف type بتاعه من:

```text
local لو واضح
LLM semantic classifier لو جديد/غامض
unknown_or_ambiguous لو الثقة قليلة
```

وأنت لا تحتاج تكتب rule لكل سؤال جديد.
أنت تحتاج:

```text
1. Types عامة قليلة
2. LLM يصنف الجديد
3. Confidence threshold
4. Analytics تسجل patterns
5. Manual review يحول المتكرر إلى shortcut
```

دي الطريقة الصح عشان النظام يكبر من غير ما تغرق في سيناريوهات.



فاهمك جدًا، وده اعتراض صحيح.
لو الـ local classifier “بيتجرأ” ويمسك أسئلة مش متأكد منها، يبقى هو مصدر التعب كله. ساعتها الحل مش إننا نحسن local rules أكتر؛ الحل إننا **نقلل صلاحيات الـ local جدًا**.

يعني بدل النظام ده:

```text
local يحاول يفهم أغلب الكلام
ولو فشل يروح LLM
```

خليه كده:

```text
local لا يفهم لغة طبيعية تقريبًا
local ينفذ فقط أوامر deterministic شبه مؤكدة
كل natural language يروح LLM semantic router
```

وده أريح لك فعلًا.

## القاعدة الجديدة المقترحة

```text
Local is not a semantic classifier.
Local is a deterministic gate only.
```

يعني local يمسك فقط الحاجات اللي عليها دليل صريح جدًا، مش “حاسس إنها كذا”.

---

# إيه اللي يفضل local؟

خلي local يمسك الحاجات دي فقط:

## 1. Pending clarification reply

لو البوت لسه سائل:

```text
Which product do you mean?
1. Light Blue
2. Acqua
3. Si
```

والمستخدم قال:

```text
1
التاني
si
acqua
```

ده local.
لأنه مش فهم لغة، ده اختيار من قائمة.

---

## 2. Exact catalog availability

لو الرسالة شكلها واضح جدًا:

```text
Do you have Light Blue?
عندك لايت بلو؟
```

ومنتج exact أو near-exact من الكتالوج.

ده local.

لكن لو:

```text
عندك حاجة لايت؟
blue
dior
```

غموض → LLM أو clarification، مش local يخمن.

---

## 3. Direct catalog command

أوامر deterministic:

```text
أغلى عطر عندك
أرخص عطر عندك
cheapest perfume
most expensive perfume
```

دي local.

---

## 4. Business info واضح

```text
طرق الدفع
مواعيد العمل
التوصيل
رقم التواصل
```

دي local من config.

---

## 5. Safety/hard guard

الحاجات اللي لازم local يحميها:

```text
allergy
excluded notes
out of stock
inactive
budget strict
non-catalog card
prompt injection
```

لكن دي guard بعد الفهم، مش classifier لغوي واسع.

---

# إيه اللي مايمسكوش local؟

أي حاجة فيها لغة طبيعية أو نية محتملة:

```text
ينفع لموعد مع خطيبتي؟
عايز حاجة تشبه ريحة الفنادق
عايز حاجة هادية بس شيك
مش عايز حاجة تبان شعبية
عايز ريحة حلوة
خليه مناسب للجامعة
مش عاجبني دول بس عايز نفس الفكرة
```

كل ده يروح LLM semantic router.

حتى لو local يقدر يلقط كلمات زي:

```text
university
work
suitable
it
```

مايمسكش إلا لو الشكل deterministic 100%.

# الحل المعماري: Local Allowlist مش Local Classifier

بدل ما تعمل local classifier يحاول يقرر من كل الرسائل، اعمل:

```text
Local Deterministic Allowlist
```

يعني local لازم يثبت إن الرسالة واحدة من الحالات المسموحة بدليل قوي.

لو مش متأكد:

```text
send_to_llm
```

مش:

```text
try local route
```

## القرار يبقى كده

```dart
if (isPendingClarificationReply(message)) {
  return localClarificationSelection;
}

if (isExactCatalogAvailability(message) && hasSingleExactCatalogMatch) {
  return localAvailability;
}

if (isDirectCatalogCommand(message)) {
  return localCatalogCommand;
}

if (isBusinessInfoExact(message)) {
  return localBusinessInfo;
}

return sendToSemanticRouter;
```

ده هيقلل جدًا misrouting.

أكبر مصدر مشاكل عندك كان:

```text
it

suitable

```

القاعدة:

```text
pronoun alone is not enough for local route
```


```text

```

لكن لو:

```text
i want it suitable for university
```

يبقى LLM.

ولو local مش 100% متأكد من question shape:

```text

```

# بدل confidence، استخدم proof requirements

أنا فاهم إن كلمة confidence ممكن تكون مطاطة.
اعمل requirements محددة.

مثال:

## Local availability لازم:

```text
message has availability verb
AND product match is exact/single
AND no recommendation/refinement language
```

لو أي شرط ناقص:

```text
LLM
```

## Product context local لازم:

```text
message is explicit question
AND product reference is resolved uniquely
AND asks about product property/suitability
```

لو فيه `want/make/change/need`:

```text
LLM
```

## Direct catalog query لازم:

```text
message contains cheapest/most expensive intent
AND asks catalog-wide query
```

# خلي LLM هو default

الـ default route لازم يبقى:

```text
semantic_router
```

مش local.

يعني بدل:

```text
detectedIntent = newRecommendation
```

من local بشكل تلقائي، خليه:

```text
detectedIntent = unknown_natural_language
action = send_to_llm
```

إلا لو local allowlist أثبت العكس.

---

# طيب التكلفة؟

أنت بنفسك قلت التكلفة عندك قليلة جدًا.
فمافيش داعي تعذب نفسك عشان توفر calls بدري.

التوفير ييجي بعدين من analytics:

```text
patterns متكررة
مضمونة
اتراجعت
تتحول local
```

لكن البداية الإنتاجية الأفضل:

```text
LLM-first for natural language
local-only for deterministic operations
```

---

# شكل النظام اللي أنصحك به

## Routing priority الجديد

```text
1. Hard safety/blocked input checks
2. Pending clarification reply local
3. Exact deterministic local commands
   - business info
   - direct catalog query
   - exact availability
4. Everything else -> LLM semantic router
5. Dart validates tool
6. Guard/render
```

ده أبسط وأقل تعب.

# إيه أعمل في الكود؟

اعمل refactor صغير اسمه:

```text
DeterministicLocalGate
```

يرجع فقط:

```text
handled
notHandled
```

مش يرجع 20 intent.

مثال:

```dart
sealed class LocalGateResult {
  const LocalGateResult();
}

class LocalHandled extends LocalGateResult {
  final LocalRoute route;
  final double proofScore;
  final List<String> proofReasons;
}

class LocalNotHandled extends LocalGateResult {
  final String reason; // "not_deterministic"
}
```

ولو `notHandled`:

```dart
sendToSemanticRouter();
```

# ممنوع local يعمل إيه؟

اكتب rules صريحة:

```text
Local gate must not classify:
- vague recommendation requests
- social/advisory turns
- emotional descriptions
- style/vibe phrases
- "make it..." refinements
- typo-heavy messages
- ambiguous pronouns except pending clarification
```

# الخلاصة الصريحة

أنت صح. النظام المتوازن القديم:

```text
local للحالات الواضحة
LLM للغامض
```

ممكن يبقى متعب لو local مش محافظ جدًا.

فخليه:

```text
LLM by default
Local only by proof
```

وده هيريحك جدًا.

## الصيغة النهائية

```text
Local لا يفهم.
Local يثبت فقط.
لو مفيش إثبات قوي، LLM يفهم.
```

ده أنسب لمشروعك لأن:

```text
LLM رخيص عندك
اللغة العربية متنوعة
العملاء هيقولوا حاجات غير متوقعة
الخطأ في local أسوأ من تكلفة worker call
```

ابدأ production كده. بعد ما تجمع data، حول المتكرر والمضمون فقط إلى local.
